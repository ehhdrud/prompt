# Review

방금 구현된 코드를 **전문가 시각으로 검토하고 잘못된 부분을 수정**하는 스킬.

직접 리뷰하지 않는다 — `fe-reviewer` / `be-reviewer` 서브에이전트에게 라우팅하여 전문 페르소나 + 독립 컨텍스트로 수행시킨다.

---

## 사용 방법

```
/review              # 방금 변경한 파일 전체 (git diff 기준 자동 감지)
/review <경로>        # 특정 파일/디렉토리
/review fe           # FE만 강제
/review be           # BE만 강제
/review fe <경로>     # FE + 범위 지정
```

---

## 워크플로우

### 1단계: 리뷰 범위 결정

- 인자 없음 → `git diff HEAD` + 스테이지 변경 + untracked 파일
- 경로 지정 → 해당 경로
- 범위가 비어 있으면 사용자에게 확인

### 2단계: FE / BE 라우팅

파일 경로 + 확장자 + **파일 내용**으로 분류한다. 확장자만으로 판정하지 말 것 — Next.js 서버 액션처럼 `.ts`/`.tsx`인데 서버 코드인 경우가 있다.

| 분류 | 힌트 |
|------|------|
| FE | `.tsx`, `.jsx`, `"use client"` 지시어, `src/components`, `src/hooks`, `.css`, `.scss`, `tailwind.config.*` |
| BE | `.py`, `.go`, `.java`, `.rb`, `controllers/`, `services/`, `repositories/`, `migrations/`, `schema.*`, `route.ts`(API Routes), `"use server"` 지시어, `actions/` 디렉토리 |
| 양쪽 | 공통 `.ts` 유틸, 타입 정의, `app/` 하위의 혼재 파일 → 양쪽 모두 디스패치 |

애매하면 사용자에게 묻는다. `fe`/`be` 강제 인자가 있으면 분류 생략.

### 3단계: 서브에이전트 병렬 디스패치

FE와 BE 파일이 모두 있으면 **한 메시지에 Agent 호출 2개**를 병렬로.

각 에이전트에 전달할 프롬프트:
- 리뷰 대상 파일 목록
- 변경 요약 (git diff 또는 직전 세션 작업 내용)
- 리뷰 기준을 적용할 것을 명시
- CLAUDE.md를 먼저 읽고 진행할 것을 명시

### 4단계: 결과 취합

각 에이전트 보고서를 그대로 사용자에게 전달. 메인 클로드가 재가공하지 않는다 — 전문가 판단을 희석시키지 않기 위함.

형식:

```markdown
# 리뷰 결과

## FE
<fe-reviewer 보고서 그대로>

---

## BE
<be-reviewer 보고서 그대로>

---

## 다음 액션
- 에이전트가 직접 수정한 항목은 이미 반영됨
- "사용자 판단 필요" 항목 중 선택할 것이 있으면 알려주세요
```

---

## 주의사항

- 자동 수정된 내용은 **바로 커밋하지 않는다.** 사용자가 확인 후 직접 커밋
- 리뷰 직후 `git diff`로 에이전트 수정분을 사용자에게 안내
- 각 리뷰어의 기준 항목 외 사소한 지적은 걸러낸다 (FE 5기준, BE 4기준 — 에이전트에 이미 지시되어 있음)
- 리뷰 대상이 너무 크면(예: 50개 파일 이상) 사용자에게 범위를 좁힐지 확인
