# Review

작업 중인 변경이 기존 프로젝트의 구조와 구현 방식을 따르는지 검토하고, 기능을 유지하는 범위에서 명확한 문제를 직접 수정한다.

## 워크플로우

### 1. 범위와 프로젝트 규칙 파악

- unstaged, staged, untracked 파일을 모두 수집하여 현재 작업 중인 변경 전체를 검토한다.
- 변경이 없으면 종료하고 사용자에게 알린다.
- 루트와 대상 경로의 `CLAUDE.md`, `AGENTS.md`, `README.md` 등 프로젝트 지침을 먼저 읽는다.
- 스타일 변경이 있으면 의존성, 설정 파일, 기존 코드를 통해 CSS, CSS Modules, Sass, CSS-in-JS, 유틸리티 CSS 등 실제 스타일 방식을 먼저 파악한다.
- 프로젝트에 스타일 지침 문서가 있으면 해당 지침을 우선 적용한다.
- Tailwind CSS v4를 실제 사용하는 경우에만 [Tailwind v4 규칙](./references/TAILWIND_V4_RULES.md)을 읽어 적용한다. 다른 버전이나 다른 스타일 기술에는 이 규칙을 적용하지 않는다.

### 2. 주변 구조 추적

- 변경 파일만 고립해서 보지 말고 import, 호출부, 상태 소유자, 데이터 흐름을 추적한다.
- 유사 컴포넌트, 훅, 서비스, 유틸, 설정, 상수와 기존 구현 패턴을 검색한다.
- 신규 추상화가 필요한지 판단하기 전에 기존 공통 구현으로 해결 가능한지 확인한다.

### 3. 품질 기준 검토

아래 기준을 순서대로 적용한다.

1. **컨벤션과 아키텍처**: 레이어, 파일 구조, 네이밍, import/export, 에러 처리, API 계약과 구현 흐름이 기존 방식과 일치하는가. 모듈 경계와 의존성 방향이 프로젝트 아키텍처를 따르는가.
2. **데이터와 상태의 SSOT**: 파생 상태나 서버 상태를 중복 저장하지 않는가. 동일한 상수, 타입, 규칙, 설정과 정책이 여러 위치에 흩어지지 않았는가.
3. **중복 제거와 중앙화**: 의미와 변경 이유가 같은 로직과 설정을 한 곳에서 관리하는가. 단순히 코드 모양만 비슷한 경우는 억지로 통합하지 않는다.
4. **책임 분리와 재사용성**: UI, 도메인 규칙, 데이터 접근, 상태 관리, 외부 연동의 책임이 명확한가. 기존 공통 모듈을 활용하는가. 새 공통화로 optional prop, 분기, override가 과도하게 늘어나지 않는가.
5. **변경 안전성과 검증 가능성**: 호출부와 영향 범위를 확인했는가. 기존 동작과 공개 계약의 호환성을 유지하는가. 숨은 사이드 이펙트와 실패 경로를 다뤘으며 관련 테스트, 타입 검사, lint 등으로 검증할 수 있는가.

변경 영역에 해당하면 다음 기본 결함도 함께 확인한다.

- UI와 상태: 불필요한 파생 state, 훅/컴포넌트 책임 혼합, 프로젝트 디자인 토큰과 스타일 작성 방식 위반
- 서버와 데이터: 입력 검증, 인증·인가, 민감정보 노출, 에러 삼키기, 트랜잭션 경계, 비동기 누락, N+1, 페이지네이션

### 4. 리팩터링

- 기능과 공개 계약을 유지하면서 영향이 명확하고 국소적인 문제는 직접 수정한다.
- 호출부까지 추적하여 수정 범위를 빠뜨리지 않는다.
- 재사용을 위한 추출·통합은 실제 중복과 변경 축이 같을 때만 수행한다.
- 광범위한 아키텍처 변경, 제품 동작 변경, 호환성 파괴, 선택지가 있는 설계는 자동 수정하지 않고 사용자 판단 항목으로 남긴다.
- 범위를 벗어난 기존 문제는 이번 변경에 필수적인 경우가 아니면 수정하지 않는다.

### 5. 검증

- 수정 후 diff 전체를 다시 읽어 의도하지 않은 변경과 누락을 확인한다.
- `git diff --check`를 실행한다.
- 프로젝트에서 확인 가능한 포맷, lint, 타입 검사, 테스트 중 변경과 관련된 최소 범위를 실행한다.
- 실패하면 원인이 이번 변경인지 기존 상태인지 구분하여 보고한다.
- 검증이 끝나기 전에는 완료로 판단하지 않는다.

## 완료 조건

다음을 모두 만족해야 리뷰 통과로 판단한다.

- 품질 기준에서 확인된 명확한 문제를 수정했다.
- 남은 항목은 사용자 판단이 필요한 트레이드오프뿐이다.
- 관련 검증이 통과했거나 실행할 수 없는 이유가 명시되었다.
- 최종 diff에 남으면 안 되는 임시 코드, 디버그 로그, 비밀정보가 없다.

리뷰 수정 여부가 아니라 **영향도와 검증 결과**로 결론을 낸다.

- 다음과 같이 동작·공개 계약·데이터 결과가 동일한 안전한 수정은 관련 검증을 통과하면 통과로 판단한다: 포맷과 정적 경고 정리, private 이름 변경과 호출부 일괄 반영, 함수·모듈 추출, 동일 로직 중복 제거, 값이 같은 상수·설정 중앙화, 의미가 동일한 canonical 스타일 문법 교체.
- 다음 변경은 사용자 확인 필요로 판단한다: 제품 동작이나 제어 흐름 변경, 공개 API·타입·스키마 변경, 데이터 저장·상태 소유권 변경, 인증·권한·보안 정책 변경, 의존성·빌드·배포 설정 변경, 마이그레이션, 호환성을 확신할 수 없는 수정.
- 이번 변경 때문에 관련 검증이 실패하면 실패로 판단한다. 검증 도구를 실행할 수 없더라도 정적 분석으로 영향도 0을 명확히 입증할 수 있으면 사유를 보고하고 통과로 판단할 수 있다.

## 결과 보고

```markdown
## 리뷰 결과

- 범위: [검토한 변경]
- 직접 수정: [수정 내용 또는 없음]
- 검증: [실행 결과]
- 사용자 판단 필요: [항목 또는 없음]
- 영향도: 없음 / 있음 / 불확실
- 결론: 통과 — 수정 없음 / 통과 — 안전한 리팩터링 / 사용자 확인 필요 — 영향도 있음·불확실 / 실패 — 검증 실패
```

## 원칙

- 근거는 프로젝트 지침과 실제 주변 코드에서 찾고 새 규칙을 임의로 만들지 않는다.
- 사소한 취향보다 결함 가능성, 유지보수 비용, 일관성에 집중한다.
- 명확한 문제는 보고만 하지 말고 수정한다.
- 수정만 하고 커밋·푸시 등 git 이력은 변경하지 않는다.
