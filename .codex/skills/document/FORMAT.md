# Document 형식 규칙

---

## 공통

### 파일명

```
{type}_title-in-english.md
```

### 저장 위치

| 타입 | 기본 경로 |
|------|-----------|
| research | `docs/research/{version}/` |
| plan | `docs/plan/{version}/` |
| task | `docs/task/{version}/` |
| task-dev | `docs/task/{version}/` (파일명 접두사 `task-dev_`로 구분) |

- `{version}`: `VERSION` 파일 참조 (예: `docs/research/vX.Y.Z/`)
- VERSION 파일이 없거나 사용자가 버전 없이 저장을 요청한 경우 버전 폴더 없이 직접 저장

### 작성 원칙

- **컨텍스트 보존**: 나중에 봐도 이해할 수 있게 배경 포함
- **핵심만 기록**: 시행착오 나열 대신 실질적인 결론/해결 과정만
- **간결하게**: 긴 대화에서 중요한 부분만 정제

## Research

특정 기능에 대한 깊은 사전 분석. 연관된 코드와 영역을 끝까지 추적하여 전체 흐름을 파악한다.

**핵심**: 표면적인 구조만 보지 않고, 연관된 기능과 영역을 **깊게** 파고들어 의존 관계와 영향 범위를 완전히 이해한다.

**주의**: 분석에 초점을 맞춘다. 문제점을 억지로 찾거나 개선 방향을 제시하지 않는다. 있는 그대로의 구조와 흐름을 정확히 기술하는 것이 목적이다.

영역 예시:
- **FE (Next.js)**: 페이지, 컴포넌트, 라우트, 스토어, 서버 액션, API 라우트
- **BE (API Server)**: 엔드포인트, 서비스, 모델, 미들웨어

```markdown
# [분석 대상 기능/페이지]

**날짜**: YYYY-MM-DD

## 목적

[이 분석이 필요한 이유, 어떤 작업을 앞두고 있는지]

## 대상 분석

[분석 대상 기능/페이지의 핵심 동작과 역할]

## 연관 영역

### [영역 1]

- 관계: [대상과 어떻게 연결되는지]
- 동작 방식
- 영향 범위

### [영역 2]

- 관계: [대상과 어떻게 연결되는지]
- 동작 방식
- 영향 범위

## 사이드 이펙트

- [이 영역을 수정할 경우 영향받을 수 있는 기능/영역]

## 참고

- [관련 코드 위치, 문서, 링크]

## 특이사항 (선택)

- [분석 중 발견한 주의할 점이 있는 경우에만 기록]

```

## Plan

구현 전 설계/계획서. 작업 범위, 단계별 접근, 의존성 등을 정리한다.

```markdown
# [작업 제목]

**날짜**: YYYY-MM-DD
**참조**: [Research 문서명](../research/파일명.md) ← 세션에서 작성했거나 지정된 Research가 있는 경우

## 배경

[왜 이 작업이 필요한지, 어떤 맥락에서 시작되었는지]

## AS-IS

[현재 상태 — 지금 어떻게 되어 있는지]

## TO-BE

[목표 상태 — 어떻게 바뀌어야 하는지]

## 구현 단계

### 1단계: [제목]

- 작업 내용
- 예상 변경 파일
- **확인 포인트**: [이 단계 완료 시 확인할 수 있는 결과/상태]

### 2단계: [제목]

- 작업 내용
- 예상 변경 파일
- **확인 포인트**: [이 단계 완료 시 확인할 수 있는 결과/상태]

## 사이드 이펙트

- [이 변경으로 영향받을 수 있는 기능/영역과 대응 방안]

## 고려사항 (선택)

- [엣지 케이스, 의존성, 리스크]

```

### 선택적 섹션

Plan 실행 후 수정이 발생한 경우, 해당 단계 아래에 **사후 수정** 섹션을 추가한다.

- 계획 단계에서는 작성하지 않는다. 실제 구현 후 계획과 달라진 부분이 있을 때만 기록한다.
- 해당 단계 내부의 마지막 위치에 추가한다.

```markdown
### N단계: [제목]

- 작업 내용
- 예상 변경 파일
- **확인 포인트**: [...]

#### 사후 수정

- [수정 내용]: [수정 이유]
```

## Task

작업 결과 요약. 공유 목적으로, 변경 전후를 명확히 전달하는 데 초점을 둔다.

> 상세 변경 내역은 커밋 로그([commit FORMAT.md](../commit/FORMAT.md) 섹션 2)를 참조.

```markdown
# [작업 제목]

**날짜**: YYYY-MM-DD
**커밋 로그**: [로그 파일명](https://github.com/{owner}/{repo}/blob/{branch}/docs/git/commit-logs/파일명.md)

## 작업 배경

[왜 이 작업이 필요했는지, 어떤 맥락에서 시작되었는지]

## AS-IS

[변경 전 상태 — 어떤 문제/한계가 있었는지]

## TO-BE

[변경 후 상태 — 어떻게 개선되었는지]

## 주요 변경

- [핵심 변경점 1]
- [핵심 변경점 2]
```

### 작성 원칙

**결과 중심으로 작성한다.** 세션 대화의 흐름이 아니라, "커밋 전 코드 대비 커밋 후 코드가 어떻게 달라졌는가"를 기준으로 기술한다. 세션에서 디버깅이나 시행착오가 많았더라도 과정에서 발생한 부수적 작업이 원래 의도를 덮지 않도록 주의.

## Task-dev

개발자·인수인계용 상세 기록. 같은 커밋 범위를 다루되 비개발자 섹션은 빼고, 데이터 변경·영향 매핑·검증 근거·코드 참조를 집중 기록한다.

### 파일명

```
task-dev_title-in-english.md
```

> `task_`와 다른 접두사라 같은 폴더에 공존 가능. 한 커밋 주제에 `task`와 `task-dev`가 함께 작성되어도 구분됨.

```markdown
# [작업 제목]

**날짜**: YYYY-MM-DD
**커밋**: [해시](https://github.com/{owner}/{repo}/commit/{hash})
**관련 문서**: [research/plan 링크] (있으면)

## 배경

[기술적으로 어떤 문제를 해결했는가. 설계 맥락·트레이드오프]

## 데이터 변경 (AS-IS → TO-BE)

### [변경 유형 1 — 예: DB UPDATE]

| 대상 | AS-IS | TO-BE | 근거 |
|---|---|---|---|
| ... | ... | ... | SELECT 결과/코드 참조 |

### [변경 유형 2 — 예: FE 하드코딩 교체]

| 대상 | AS-IS | TO-BE | 위치 |
|---|---|---|---|
| ... | ... | ... | `file:line` |

## 영향 범위

### 직접 영향 (현재 화면 가시)
- [항목] — [근거]

### 간접 영향 (BE 동기화·미래 가시)
- [항목] — [언제 가시화될지]

### 영향 없음 (검증 완료)
- [항목] — [왜 영향 없는지. 검증 SQL/코드 참조]

## 신규 자원 (new)

이번 커밋으로 **처음 도입**되는 개념·모듈·카테고리를 정리. 기존 교체와 구분.

- [자원 이름]: [의미·동작·확장 지점]

## 검증 근거

매핑·영향 결정을 내린 근거. 재현 가능하게 SQL·코드 참조·테스트 방법 기록.

- [결론] ← [근거 SQL / 코드 추적 경로 / 수동 확인 방법]

## 코드 참조 (빠른 인덱스)

| 파일 | 역할 |
|---|---|
| `file:line` | [이 작업에서 무엇을 담당] |

## 후속 작업 (follow-up)

본 커밋에서 의도적으로 제외한 항목. 어디에·언제 필요한지.

- [항목] — [트리거 조건 / 담당 영역]
```

### 작성 원칙

- **비개발자 요약은 포함하지 않는다** (task에는 있음).
- **숫자·정점 인덱스·SQL·파일 경로는 구체적으로** 기재. "대략", "몇 개" 같은 모호 표현 금지.
- **검증 근거를 반드시 동반**. "확인했다"는 말 대신 실제 SQL, grep 결과, 코드 라인 번호.
- **세션 대화에서 나온 시행착오의 교훈**이 설계 결정에 영향을 줬으면 `검증 근거`에 짧게 남긴다 (상세는 플랜의 사후 수정으로).
- **`new` 섹션**은 기존 자원과의 차이를 명확히. "이게 뭔지"보다 "왜 기존 자원으로 못 했는지"를 짚는다.
