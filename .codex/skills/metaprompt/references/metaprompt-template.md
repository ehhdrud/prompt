# 메타프롬프트 설계 절차와 골격

Anthropic 메타프롬프트 노트북의 절차를 기본으로 하고, 유형별 골격과 산출물 형식을 더한 것이다.

기준일: 2026-10-23

## 목차

1. 설계 절차 (Inputs → Structure → Instructions)
2. 변수 규칙
3. 골격: 시스템 프롬프트
4. 골격: 태스크(유저) 프롬프트
5. 골격: 툴 설명
6. 산출물 형식 (설계 메모, 검증 제안)

---

## 1. 설계 절차

Anthropic 메타프롬프트는 산출물을 세 단계로 만든다. 그대로 따른다.

1. **`<Inputs>`**: 프롬프트가 실행 시 받을 **최소한의** 가변 입력을 나열한다. 고정 정보(서비스명, 정책)는 변수가 아니라 본문에 넣는다.
2. **`<Instructions Structure>`**: 변수를 어디에 둘지, 섹션 순서를 어떻게 할지 계획한다. **긴 입력(문서, 코드, FAQ)은 그것을 사용하는 지시보다 앞에** 둔다.
3. **`<Instructions>`**: 최종 프롬프트를 쓴다.

작성 규칙:
- 산출물은 "열정적이고 유능하지만 경험이 없고 세상 물정 모르는 AI 비서"에게 주는 지시문이다. 일관되고 정확한 수행에 필요한 것을 모두 담되, 그 이상은 담지 않는다.
- 점수·판정을 요구할 때는 **근거를 먼저** 쓰고 점수를 쓰게 한다.
- 스크래치패드·내부 독백은 **복잡한 과제에만** 넣는다. (Claude 5.x에서는 추론을 출력에 쓰라고 하지 말고 짧은 근거 요약만 요청한다. claude-guide.md §4)
- 출력 태그 이름은 지정하되 닫는 태그까지 써 줄 필요는 없다.
- 메타프롬프트는 과제를 **대신 수행하지 않는다**. 산출물은 항상 지시문이다.

메타프롬프트 노트북의 워크드 예시 유형 (참고용 패턴):

| 유형 | 핵심 장치 |
|---|---|
| FAQ 기반 CS 에이전트 | FAQ만으로 답변, 범위 밖·답 없는 질문 거절, 적대적 사용자 대화 종료, `<thinking>`에 FAQ 인용 후 `<answer>` |
| 문장 비교 | 출력을 `[YES]`/`[NO]`로 시작 |
| 문서 Q&A | 번호 인용 목록 → 대괄호 인용 번호를 단 답변, 고정 예시 형식 |
| 소크라테스식 수학 튜터 | 내부에서 먼저 풀고, 학생 단계마다 정해진 문구로 점검, 답 대신 힌트 |
| 함수 호출 비서 | 제공된 함수만 사용, 오류 시 재시도, 함수로 답할 수 없으면 거절 |

## 2. 변수 규칙

- 변수는 `{{VARIABLE_NAME}}` 형태로 쓴다. (노트북 원형은 `{$NAME}`이며, 대상 템플릿 엔진에 맞춰 통일한다.)
- 각 변수는 프롬프트에서 **한 번만 치환**되고, 이후 본문에서는 괄호 없이 "the document", "the user's question"처럼 자연어로 가리킨다.
- 변수는 XML 태그로 감싼다: `<document>{{DOCUMENT}}</document>`.
- 입력이 여러 개면 `<documents>` 아래 `<document index="n"><source>…</source><document_content>…</document_content></document>`.

## 3. 골격: 시스템 프롬프트

순서는 권장안이다. 과제에 필요 없는 섹션은 뺀다.

```text
[역할·목적] 한두 문장. 누구를 위해 무엇을 하는 비서인지, 상호작용 환경(채팅/에이전트/파이프라인).

[맥락·동기] 사용자·제품·도메인 정보, 왜 이 규칙들이 중요한지. 규칙마다 이유가 붙을 수 있게 여기서 배경을 준다.

<reference>  (선택, 긴 자료는 지시보다 앞)
{{FAQ_OR_DOCS}}
</reference>

<instructions>
1. 핵심 동작을 번호 목록으로. 순서·완전성이 중요할 때만 번호.
2. 해야 할 것을 서술한다. "하지 마라"가 필요하면 대신 할 행동을 함께 쓴다.
3. 범위 밖 요청, 정보 부족, 모호함을 어떻게 처리할지. 추측 대신 "모른다"고 말할 권한을 준다.
4. 툴이 있으면 언제 쓰는지 보통 어조로. 병렬 호출 가능 여부.
5. 에이전트면: 어디까지 자율적으로 진행하고 언제 멈춰 확인할지 (파괴적·되돌리기 어려운·외부에 보이는 동작).
</instructions>

<examples>
<example>
<user>…</user>
<response>…</response>
</example>
(2~5개, 실제와 비슷하고 서로 다른 유형, 엣지 케이스 포함)
</examples>

<output_format>
형식, 길이, 언어, 태그. 긍정형으로. 필요하면 템플릿.
</output_format>

[마무리 규칙] 완료 조건, 자체 검증 기준("Before you finish, verify … against …").
```

플랫폼별 조정:
- **Claude**: XML 태그 구조, `<example>` 사용, prefill·`<thinking>` 요구 없음, 강조어 최소.
- **GPT/Codex**: 마크다운 헤더 구조(`# Role and Objective` …), 긴 컨텍스트면 지시를 앞뒤 양쪽에, 에이전트면 persistence/tool-calling/planning 리마인더, 마크다운 출력은 명시적으로 켜기.

## 4. 골격: 태스크(유저) 프롬프트

한 번의 요청으로 결과를 받는 프롬프트. 시스템 프롬프트가 있으면 중복하지 않는다.

```text
<documents>  (긴 입력은 맨 위)
{{INPUT}}
</documents>

[과제] 동사로 시작하는 한두 문장. 범위를 넘는 것을 원하면 명시 ("Go beyond the basics…").

[제약] 길이, 대상 독자, 포함·제외 항목, 언어.

[절차] (선택) 긴 문서면 "관련 구절을 <quotes>에 먼저 인용한 뒤 …"

[출력 형식] 긍정형. 예시 하나.

[검증] "Before you finish, verify that …"
```

Claude Code / Codex에 보내는 작업 지시면 claude-code-guide.md §3의 Before/After 표를 따른다: 파일·패턴·증상·"고쳐진 상태"를 구체적으로, 실행 가능한 검증 수단을 포함.

---

## 5. 골격: 툴 설명

```text
name: <snake_case, 동사+대상>
description: |
  무엇을 하는지 한 문장. 언제 쓰는지 (그리고 언제 쓰지 않는지) 한두 문장.
  반환값의 형태. 부작용·비용이 있으면 명시.
parameters:
  <name>: 의미, 형식, 예시 값, 필수 여부. 추측하지 말아야 할 값은 "ask the user if unknown".
```

- 복잡한 사용 예시는 설명에 넣지 말고 프롬프트의 `# Examples` 섹션에.
- MCP 툴은 `Server:tool_name`으로 참조.
- "CRITICAL: ALWAYS use…" 같은 강조는 쓰지 않는다.

- 대상: <플랫폼/모델>, 유형: <시스템/태스크/SKILL/에이전트/툴>
- 입력 변수: `{{A}}`(…), `{{B}}`(…)
- 적용 원칙: <가이드 섹션 번호와 한 줄 근거> × 3~6
- 가정: <확인하지 못해 가정한 것>
